# Dataset

The evaluation dataset for `guideline-gpt`. See
[ADR-003](docs/decisions/003-dataset-construction.md) for the rationale.

> ⚠️ **The committed dataset is synthetic.** It is generated by
> `scripts/generate_synthetic_data.py` to exercise the harness end-to-end while
> the real corpus is pending. It mirrors the shape a real set would have (75
> questions, 15 hard cases, slice tags) but the text and answers are
> placeholders. The construction *workflow* below is what a real set follows.

## Files

| File | Contents |
|---|---|
| `eval_dataset/questions.jsonl` | The full set — one `EvalQuestion` per line. |
| `eval_dataset/hard_cases.jsonl` | The 15 hard cases (also flagged in the full set). |
| `eval_dataset/corpus_manifest.json` | The corpus snapshot: documents and the set of valid chunk ids. |

## Schema

Each line serializes `eval_harness.types.EvalQuestion`:

| Field | Meaning |
|---|---|
| `question_id` | Stable unique id. |
| `question` / `ground_truth_answer` | The question and its reference answer. |
| `relevant_chunk_ids` | Chunk ids that should be retrieved to answer it. |
| `source_documents` | Source document filenames. |
| `difficulty` | `easy` \| `medium` \| `hard`. |
| `question_type` | `factoid` \| `synthesis` \| `comparison` \| `ambiguous`. |
| `is_hard_case` | True for the 15 hand-crafted hard cases. |
| `rationale` | Why a hard case is hard (hard cases only). |

## Composition

- **75 questions:** 30 easy, 30 medium, 15 hard.
- **15 hard cases** (`is_hard_case=True`), the hand-crafted ones requiring domain
  reasoning beyond surface retrieval.
- Spread across difficulty and the four question types so the dashboard can break
  results down by slice.

## Construction workflow (for a real set)

1. Generate ~150 candidate Q&A pairs grounded in corpus chunks with a strong LLM.
2. Curate down to ~60: keep/edit/reject, dropping questions whose answer is
   trivially in the phrasing or that say "according to the passage".
3. Hand-write 15 hard cases from domain expertise.
4. Validate: `eval-harness validate-dataset` (and CI) confirms every
   `relevant_chunk_ids` entry exists in the corpus manifest, ids are unique, and
   required fields are populated.

## Validation

`dataset/validator.py` runs in CI: a question that references a chunk id absent
from the corpus would silently zero out its retrieval metrics, so this is caught
at build time rather than discovered in the results.
